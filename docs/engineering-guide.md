## Ground rules

- Be clear and concise. Sacrifice grammar for brevity in comments and replies.
- Never commit or push. Leave changes in the working tree for review.
- Don't ask the developer to run a command you can run yourself.
- Ask before changing a package you don't own, and explain why.
- Reuse first: before you write a component, CSS rule, helper, or SQL
  function, search for an existing one.
- Put business logic in SQL. TypeScript only orchestrates: it doesn't
  re-validate what the OpenAPI schema validates, and it moves data between the
  database, the network, and templates.

## Package architecture

Split by consumer, not by layer. Builder has three packages. Start with the
ones you need.

```
packages/
	app/       {{SCOPE}}/app     Backend + dashboard. Owns openapi.yaml, sql/, migrations/.
	client/    {{SCOPE}}/client  Typed SDK generated from app's openapi.yaml. No server code.
	agent/     {{SCOPE}}/agent   (Optional) MCP server / CLI built on client.
```

Rules:

1. `packages/app/openapi.yaml` is the single source of truth for every
   operation. Generators in `app/scripts/` write the types into `client` (and
   the MCP tool schemas into `agent`). Generated files end in `.gen.ts`, are
   committed, and CI fails on drift (`npm run gen:check`).
2. `client` exposes a browser-safe `/api` subpath (`Client.call(operationId,
   { params, query, body })`) with no Node-only imports. The package root
   re-exports the exact same types. Never duplicate transport or schema types.
3. Import across packages only through `{{SCOPE}}/<package>`. The one exception
   is test utilities, in test files.
4. Each package has an `AGENTS.md` that lists its role, layout, and
   package-specific rules. The root `AGENTS.md` holds repo-wide rules and tells
   agents to read every `packages/*/AGENTS.md`.

### Request flow

1. CORS, `/healthz`, Better Auth mount (before the body parser).
2. JSON and urlencoded parsers (4 MB limit, raw body kept for webhooks).
3. Attach `req.pg`, `req.auth`, `req.pgmb`; best-effort `resolveViewer`.
4. Request id (from `X-Request-Id`, max 64 chars, else UUID), `pino-http`.
5. Static `/public` (hashed `dist/` = `immutable, max-age=1y`; rest 1h).
   Everything else defaults to `Cache-Control: no-cache`.
6. In development, Vite in middleware mode.
7. `express-openapi-validator`: `coerceTypes`, `removeAdditional`,
   `discriminator`, `validateFormats`, multer memory uploads. Its resolver maps
   `operationId` to `src/routes/<operationId>.ts(x)`; a missing file returns
   501.
8. The page middleware enforces `BearerAuth` when every security alternative
   requires it, calls the handler, and sends the returned string as HTML. A
   handler that returns `undefined` has sent its own response.
9. Errors: full-page HTML requests get the `ErrorPage` route; JSON and every
   htmx request get `application/problem+json`
   (`{ type, title, status, detail, instance: requestId }`).

### One route, two surfaces

Each route serves HTML and JSON from the same handler by content negotiation:

```tsx
export default async function GetThing(req: ITypedExpressRequest<'GetThing'>) {
	const viewer = req.authMetadata!
	const [row] = await getThing.run(
		{ id: req.params.thingId, viewer_id: viewer.id },
		req.pg,
	)
	assert(row?.j, notFound('Thing not found'))
	if(shouldSendJson(req)) {
		req.res!.json(row.j)
		return
	}

	return <Layout seo={{ title: row.j.name }}>…</Layout>
}
```

Mutations called from htmx forms return `204` + `HX-Redirect` (or
`HX-Trigger`); JSON callers get `201` and the resource (`sendOrRedirect`).

### Adding a route

1. Add the operation to `openapi.yaml`. Type and bound every input:
   `maxLength`, `maxItems`, `maxProperties`, `minimum`, `maximum`, `enum`,
   `format`. Declare `security`, `default: ProblemResponse`, and only the
   status codes that are part of the contract (404 on a GET, 409 on a
   conflict). Use opaque cursor pagination (`cursor` in, `nextPageCursor` out).
2. Run `npm run gen`.
3. Add the query to `sql/queries.sql` and run `npm run pgtyped:typegen`.
4. Write `src/routes/<OperationId>.ts(x)` with `ITypedExpressRequest<'Op'>`.
   Don't re-validate what the schema validates.
5. Add an end-to-end test.

## Database design

All SQL lives in `.sql` files in `packages/app/sql`. No inline SQL in
TypeScript.

### Schema conventions

- One app schema, `{{SCHEMA}}`. Extensions (`pgcrypto`, `citext`, `pg_trgm`) go
  in `public`. Every function sets `SET search_path = {{SCHEMA}}, public`
  (except inlinable SQL functions, which must not have a `SET` clause).
- The pool pins `options: '-c search_path={{SCHEMA}} -c timezone=UTC'`, because
  SQL builds API timestamps and they must not depend on the server's time zone.
- Primary keys: `UUID DEFAULT gen_random_uuid()`.
- Audit columns on every mutable table: `created_at`, `created_by`,
  `updated_at`, `updated_by` (`TIMESTAMPTZ NOT NULL DEFAULT now()`).
- Soft state through enums: `entity_status AS ENUM ('ACTIVE', 'ARCHIVED')`,
  `entity_visibility AS ENUM ('PRIVATE', 'PUBLIC')`. Enum values are
  UPPER_SNAKE.
- Value-kind domains hold validation in one place: `safe_url`,
  `email_address` (CITEXT), `money_amount NUMERIC(12,2) CHECK (>= 0)`,
  `usage_count INTEGER CHECK (>= 0)`, `hex_color`, slugs, and so on. Map each
  domain to a TS type in `pgtyped.config.json` `typesOverrides`.
- `CHECK` constraints for lengths and shapes on every text column. Money is
  `NUMERIC`, never float.
- Invariants live in the database: triggers for immutability (for example,
  published versions can't change), provisioning (a default org on user
  insert), and protection of system rows.
- Enforce authorization per query, not with RLS. Every query takes
  `:viewer_id` and filters through helper functions such as
  `user_can_edit_org(user, org)` and `user_can_own_org(user, org)`, which
  centralize the admin bypass.
- JSON shapes are built in SQL by `<entity>_json(row, …)` functions that
  return `jsonb` matching the OpenAPI schema, so routes stream `row.j`
  straight to `res.json`.
- Caches and derived indexes are `UNLOGGED` tables, rebuilt by a worker when
  empty.
- Comment every table, non-obvious column, and function with why it exists.
  Section headers look like `-- ─── users ───────`.

### Query conventions (`queries.sql`)

- One `/* @name PascalCaseName */` per query, followed by a comment that says
  what it does and which route uses it.
- Required params use `:param!`. Qualify table names with `{{SCHEMA}}.`.
- Write multi-step mutations as one statement with CTEs (`WITH new_x AS
  (INSERT … RETURNING *), seed AS (…) SELECT …`), so they're atomic without a
  TypeScript transaction.
- Guard quotas and permissions inside the statement
  (`WHERE {{SCHEMA}}.assert_x_limit(:viewer_id!)`); `assert_*` functions raise
  coded errors that `mapError` turns into Boom errors.
- Partial updates `COALESCE` every nullable param; use an explicit `:clear_x`
  flag to set NULL.
- Insert composites with
  `SELECT * FROM jsonb_populate_record(null::t, :data::jsonb)`.
  Read composites with `to_jsonb(t)`.
- Keyset pagination on `(updated_at, id)` descending; never `OFFSET`.
- Search with `pg_trgm` GIN indexes (`ILIKE`) or `tsvector`
  (`websearch_to_tsquery`).

### Migrations

1. Edit `sql/ddl.sql` (the desired state).
2. Run `npm run migrate:plan` to generate the migration, then hand-qualify
   table names with `{{SCHEMA}}.`.
3. Ship one migration file per PR.
4. `npm run pgtyped:typegen` drops the schema, applies all migrations to the
   local Docker Postgres, and regenerates `src/queries.ts`.

## TypeScript style

- Tabs, LF, final newline, 80-column soft limit (`.editorconfig`). YAML and
  JSON use two spaces.
- `.ts` extension on every relative import.
- `#private` members in classes.
- Infer types; annotate only to resolve ambiguity.
- Nested function declarations go at the end of their parent function.
- `assert(cond, boom.notFound('…'))`, not `if (!cond) throw`. Don't create
  custom error classes.
- Optional assignment with `||=` or `??=`.
- No casts unless unavoidable, and then with a comment explaining why. Never
  `as any` or `as unknown`.
- No `console.log`; use `LOGGER`.
- Files: routes are `PascalCase` operation ids, components are `PascalCase.tsx`,
  everything else is `kebab-case.ts`.
- Comments explain why, not what. Document load-bearing settings in place (see
  Builder's `db.ts`, `vite.client.config.ts`, `Dockerfile`).

From `DESIGN.md`:

- 2px corners, 1px borders, no resting shadow.
- Canvas color + noise texture + centered scroll-linked guilloche.
- Glass lift and cursor glow on cards and forms; glow without lift on
  reporting tiles; tables, plots, and navigation stay still.
- Tabular numerals for metrics, ids, timestamps, and prices.
- Light and dark themes; red danger treatment in both.
- Visible 2px racing-blue focus outline; respect `prefers-reduced-motion`.
- Responsive: 900px shell breakpoint, 248px sidebar above it, bottom tabs and
  menu sheet below it; grids collapse by 560px; 44px touch targets.

Use public `rc-` classes and `data-variant` / `data-tone` attributes
(`<button class="rc-button" data-variant="primary">`). Call
`initReclaimBehaviors(document)` once in the browser entry.

### Markup rules

1. Keep the DOM flat.
2. Space with `padding` and `gap`, not `margin`.
3. Hover transitions are `0.1s`.
4. Never draw your own icons; use the `Icon` component. If no icon fits, ask.
5. Semantic elements first: `<button>`, `<header>`, `<section>`, `<aside
   role="status">`. Not `div` by default.
6. Use the shared `Dialog` component: close button top right, actions in
   `footer`, no "Cancel" button, no dialog on a dialog.
7. Forms use `HxForm`; 4xx bodies go into `.form-error`, other errors become a
   toast.
8. Escape all dynamic text (`escapeHtml`, `markup`). Run the XSS scan
   (`@kitajs/ts-html-plugin` `xss-scan`) in `npm run check`.
9. Every public page fills `Layout`'s `seo` prop (title, description,
   canonical, OG image, JSON-LD); private pages set
   `robots: 'noindex, nofollow'`.
10. Browser JS is progressive enhancement: delegated listeners on `document` in
    `src/client/*.ts`, so htmx swaps need no rewiring. Never hard-code a
    `/public/dist/…` URL; resolve it through the Vite manifest.

## Background work

Use pgmb, not an external queue. Producers publish inside the request's
transaction through `req.pg`. Consumers live in `src/worker/*.ts`, are
registered in `worker/register.ts`, and run on a separate pool (pgmb
changes the session `search_path`). Push live updates to the browser with SSE
fed by pgmb events, not polling.

## Tests

- Native `node:test`. Run one file: `node --test <file>`; one case:
  `--test-name-pattern`.
- Database: a gzipped PGlite snapshot of all migrations
  (`createSeededPglite()`), warmed in `pretest`. No Docker needed for tests.
- End-to-end first: `bootApp()` per `describe`, real HTTP with `fetch`, real
  sign-in, unique emails and slugs per test.
- UI tests use `happy-dom` and dispatch real click and keyboard events.
  Set `element.files = null` before submitting a non-file input through htmx.
- Test behavior, not implementation. Don't add a test for B when A's test
  already covers A → B → C, unless B has an uncovered edge case.
- Mock fetch through constructor options; don't stub globals.

## Definition of done

Before you report a task done:

1. `npm run lint:fix` and `npm run check` pass from the root.
2. `npm run gen:check` passes.
3. The relevant tests pass (`node --test <file>`), and new behavior has an
   end-to-end test.
4. Schema changes are in exactly one new migration, and `src/queries.ts` is
   regenerated.
5. Report what you changed, what you ran, and anything you skipped or couldn't
   verify. Don't commit.

## How to run this with multiple agents

For large features, one planning agent (Opus) splits the work into parallel
workstreams with exclusive file ownership and gives them to implementation
agents (Sonnet). Typical split: (1) `openapi.yaml` + codegen, (2) `ddl.sql` +
`queries.sql`, (3) routes, (4) components + CSS + client JS, (5) tests. The
planner owns the migration: it runs `npm run migrate:plan` once at the end.
